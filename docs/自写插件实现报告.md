# 自写插件实现报告(v0.4.x 自研能力)

> 能力：Agent 用 `install_plugin` 自己生成插件（自动生成 manifest + index.js），校验通过即热加载，无需重启即可在下一轮对话调用；配套 list/read/remove/reload 全生命周期管理。

## 一、新增能力

| 工具 | 作用 |
|---|---|
| `install_plugin(name, description, code, overwrite?)` | 校验 → L3 用户确认 → 落盘 → 缓存失效 → 热加载；覆盖更新版本号自动 +1 |
| `list_plugins()` | 列出插件、来源（自写/外部）与可用工具 |
| `read_plugin(name)` | 读取 manifest.json + index.js 源码（便于修订） |
| `remove_plugin(name)` | L3 确认后删除，立即失效 |
| `reload_plugins()` | 全量 require 缓存失效 + 重扫（手动改文件后使用） |

插件工具按 `plugin_<插件名>__<工具名>` 注入模型工具列表；该注入此前缺失（执行链路存在但 schema 未进 LLM），本版补齐。安装/删除后主进程推送 `plugins:changed`，插件页实时刷新。

## 二、协议与沙箱

```js
module.exports = { tools: [{
  name: 'hello', description: '打招呼', params: { who: 'string' },
  run(args, ctx) { ctx.log('hi'); return 'hello ' + (args.who || 'world') },
}] }
```

- 静态校验不执行 `run`：顶层仅允许 `require('path')`，无 fs/process/timer；名称/描述/参数数/代码 64KB 白名单
- 运行时 vm 与校验共用 `createHardenedContext`：`codeGeneration.strings=false` 封堵 `constructor.constructor("return process")` 经典逃逸；文件/命令仍走 ctx.tools.run 桥接（工作目录限制 + L4 危险命令拦截）
- 安装与删除走 L3 风险确认卡；首次调用每个插件工具沿用既有 allow/deny/ask 权限

## 四、验证口径

- 校验：非法名/路径穿越、缺 run、工具名含 `__`、超长、顶层 fs 依赖全部拒绝；恶意 `run` 不触发
- 逃逸：`Function("return process")` 与 `eval` 均被阻断；普通函数声明不受影响
- 热加载：安装后 schema 立即产出；覆盖更新版本 1.0.0→1.0.1 且元数据立即换新；外部改文件后 `reload_plugins` 生效
- 门禁：typecheck / eslint（0 error）/ vitest 50 文件 300 用例 / vite+tsc build 全绿

## 五、审计发现并修复的老问题

| # | 问题 | 修复 |
|---|---|---|
| 1 | 插件启用/禁用是假开关：状态存 memory.json，v0.4.0 SQLite 迁移后既不落库、loadMemory 也不返回，主进程从不读取 | 状态迁至 settings.json `general.pluginStates`，schema 注入与执行前都检查；新增 `plugins:getState/setState`；渲染层设置全量保存时合并保护该字段 |
| 2 | 插件 `run()` 同步死循环可冻结整个应用（10s 超时对同步代码无效） | `run` 改为在 vm 脚本内调用，script 超时可直接中断同步循环；外层保留 async 超时兜底 |
| 3 | 元数据用 `require(index.js)` 加载：第三方插件顶层代码以主进程权限执行 | 改为 vm 静态加载（顶层仅 path、10s 超时、禁代码生成逃逸），不再 require |
| 4 | UI 安装/删除插件不失效主进程 spec 缓存（最长 15s 陈旧窗口） | install/delete 落盘后失效缓存 |
| 5 | pluginPerm 直接 writeFileSync 写 settings.json，与原子写并发可能截断 | 统一 writeFileAtomic |

## 六、进程隔离(已落地)

- 插件执行迁入 utilityProcess 独立进程：每次调用 fork 子宿主，父子间走 MessagePort 协议，所有特权操作(读/写/执行命令)由子进程回问父进程统一裁决，子进程不持有 fs/命令/确认能力
- 挂死强杀：父进程 120s 总看门狗超时直接 kill 子进程(同步死循环另由宿主内 vm script 10s 超时打断)；子进程崩溃返回错误、主进程存活
- 逃逸面收敛：宿主内 process.env 清空、`process.getBuiltinModule`/`binding` 置空、`require` 全禁、`codeGeneration.strings=false` 封堵 Function 逃逸
- 插件桥接的 `exec_command` 已与主工具同源：L4 拦截 + L2/L3 变更确认（风险卡/永久放行/自动批准均复用），插件级异步兜底从 10s 提至 120s 以容纳 60s 确认
- 兜底：utilityProcess 启动异常(极端打包环境)时回落同进程 vm，权限边界与协议不变，仅失去进程隔离

## 七、验证口径(进程隔离)

- 单测：host-core 协议(正常/桥接/同步挂死/异步挂死/逃逸阻断) + policy 裁决(路径限制/L4/确认拒绝) + 兜底链路端到端，54 文件 321 用例全绿
- Electron 冒烟：正常插件跨进程读写、死循环 3s 强杀、run 抛异常主进程存活、变更命令被拒，四场景通过
- asar 实测：把宿主打进 app.asar 后 `utilityProcess.fork` 正常加载并完成桥接调用(消除打包加载疑虑)

## 八、已知边界

- utilityProcess 仍是同用户权限进程：若插件同时逃逸 vm 与代码生成开关，理论上可经其自身进程读取磁盘文件；真正的数据隔离需要 OS 级沙箱(低权限 token/AppContainer)，已超出桌面应用常规范围
- 定时任务/无窗口场景下安装确认会 60 秒超时自动拒绝（安全默认）
